# Critic 与核心模型接口规范

[中文](#chinese) | [English](#english)

本文说明 `src/agent/critic.py` 的统一接口，重点约束各类 Critic 的核心模型。Critic 根据某一步的输入估计后续累计回报。模型负责读取字段和计算价值，优势计算、训练目标、损失和参数更新由后续训练组件负责。

## 1. Critic 输出什么

当前 PPO 框架使用状态价值，记作 `V`，表示从当前情况开始，按策略继续运行时预计能获得多少累计奖励。每列车输出一个价值，中央 Critic 也可以选择输出整个团队的一个价值。

| 输出模式 | 格式 | 含义 |
|---|---|---|
| 逐列车价值 | `dict[int, Tensor]` | 每个整数列车编号对应形状为 `(1,)` 的浮点张量 |
| 团队价值 | `Tensor`，形状为 `(1,)` | 整个团队预计获得的累计回报 |

Critic 模型的输出可以为正、零或负，数值范围与所用奖励有关。Actor 每列车输出五个动作分数，Critic 每列车输出一个状态价值。两者可以使用不同模型、参数共享方式和信息范围。

## 2. 统一输入接口

三种 Critic 都通过下面的方式调用：

```python
values = critic(
    observations,
    current_infos,
    additional_infos=additional_info,
)
```

| 参数 | 格式 | 内容 |
|---|---|---|
| `observations` | `dict[int, Any]` | 某一步所有列车的官方观测 |
| `current_infos` | `dict[str, dict[int, Any]]` | 同一步的官方 info，先按类别、再按列车编号读取 |
| `additional_infos` | `dict[str, Any]` 或 `None` | 外部提供的额外信息，默认 `None` |

三项输入对应同一个时间步。地图、列车位置、任务安排、时间表和进度等信息由外部读取或维护，按模型约定放入 `additional_infos`。Critic 将它原样传给模型。

Critic 的参数名使用 `additional_infos`；当前 Actor 的对应参数名为 `addtional_infos`，调用时按各自代码中的名称传入。

## 3. 三种 Critic 的模型组织方式

| Critic | 构造方式 | 模型调用方式 | 输出 |
|---|---|---|---|
| `IndependentCritic` | `IndependentCritic(models)` | 遍历列车模型字典，各列车调用自己的模型 | 逐列车价值字典 |
| `ShareNetworkCritic` | `ShareNetworkCritic(model)` | 遍历观测字典中的列车编号，分别调用同一个模型 | 逐列车价值字典 |
| `CentralizedCritic` | `CentralizedCritic(model, team_value=False)` | 一次调用联合模型 | 由 `team_value` 决定 |

核心模型继承 `torch.nn.Module`。基类 `Critic` 的 `model` 初始为 `None`，子类设置具体模型。基类 `forward` 直接调用 `_get_values`，具体子类实现模型组织和调用。

## 4. 独立模型与共享模型规范

### 4.1 核心模型输入

这两类 Critic 使用同一个单列车模型接口：

```python
model(
    observations,
    current_infos,
    additional_infos=additional_info,
    agent_id=agent_id,
)
```

对应的模型入口为：

```python
def forward(
    self,
    observations,
    current_infos,
    *,
    additional_infos=None,
    agent_id,
):
    ...
```

`agent_id` 指定本次为哪列车估计价值。模型收到完整字典，用 `observations[agent_id]` 读取本列车观测，用 `current_infos["speed"][agent_id]` 等方式读取辅助信息。是否使用其他列车或全局数据，由模型与实验条件约定。

### 4.2 核心模型输出

单次调用返回形状为 `(1,)` 的 PyTorch 浮点张量，保留梯度。例如值为 `[5.0]`，表示预测该列车从当前时刻继续运行能获得约 5 的累计回报。实际返回值来自网络计算。

Critic 收集各模型结果后，按整数列车编号组成字典：

```python
import torch

values = {
    0: torch.tensor([5.0]),
    1: torch.tensor([8.0]),
}
```

上述例子仅说明数据格式。模型使用实际网络输出，每个值保持 `(1,)`，方便后续统一组织训练张量。

### 4.3 构造模型

独立 Critic 接收整数编号到模型对象的字典。每列车创建自己的模型实例，网络结构可以相同，参数分别管理。

```python
from src.agent.critic import IndependentCritic

critic = IndependentCritic({
    0: TrainValueModel(...),
    1: TrainValueModel(...),
})
```

内部使用 `nn.ModuleDict` 注册模型。存储键转换成字符串，输入和输出的列车编号仍使用整数。PyTorch 可以通过 `critic.parameters()` 收集全部模型参数。

共享 Critic 接收一个模型，各列车使用相同参数，根据 `agent_id` 分别计算价值。

```python
from src.agent.critic import ShareNetworkCritic

critic = ShareNetworkCritic(TrainValueModel(...))
```

`TrainValueModel` 表示团队实现的核心模型类，`...` 表示该模型的构造参数。当前实现按列车逐次调用模型。

## 5. 中央 Critic 与 team_value

### 5.1 核心模型输入

中央 Critic 将全部输入交给模型，并把构造时的 `team_value` 作为关键字参数传入：

```python
model(
    observations,
    current_infos,
    additional_infos=additional_info,
    team_value=team_value,
)
```

核心模型接受下面的入口：

```python
def forward(
    self,
    observations,
    current_infos,
    *,
    additional_infos=None,
    team_value=False,
):
    ...
```

模型根据 `team_value` 选择输出模式。需要同时支持两种模式的模型，可以设计逐列车输出和团队输出两个部分；只支持一种模式的模型，在模型说明中写明可用设置。

### 5.2 两种输出模式

| 设置 | 模型必须返回 | 预测目标 |
|---|---|---|
| `team_value=False` | 整数列车编号到 `(1,)` 浮点张量的字典 | 各列车后续的累计回报 |
| `team_value=True` | 一个形状为 `(1,)` 的浮点张量 | 团队后续的累计回报 |

开关默认 False。中央模型可以读取全局信息，同时为各列车分别输出价值；选择团队模式时，输出一个团队价值。输出范围与读取信息范围分别由模型和实验设置说明。

中央 Critic 检查输出是否符合所选模式：团队模式要求 `(1,)` 张量，逐列车模式要求字典。字典中的编号、各张量形状和数值由模型按本规范提供。

### 5.3 构造方式

```python
from src.agent.critic import CentralizedCritic

critic = CentralizedCritic(JointValueModel(...), team_value=False)
team_critic = CentralizedCritic(JointValueModel(...), team_value=True)
```

`JointValueModel` 表示联合处理输入的核心模型。每次 Critic 调用只调用一次该模型。

## 6. 模型共同遵守的约定

| 项目 | 要求 |
|---|---|
| 输出 | 返回有限数值的浮点张量，单个价值形状固定为 `(1,)` |
| 梯度 | 直接返回网络计算结果，保留从参数到价值的计算过程 |
| 设备 | 模型输入与参数使用兼容设备，调用方可使用 `critic.to(device)` 移动模型 |
| 缺失数据 | 处理观测为 `None` 的情况；需要额外字段时明确说明必需输入 |
| 输入说明 | 记录所需观测类型、特征长度、辅助字段和额外信息范围 |
| 历史输入 | 根据传入数据计算，训练时可以对保存的历史样本重新前向计算 |
| 输出范围 | 逐列车输出准确对应列车编号；团队输出与团队奖励目标对应 |

在模型计算结果上调用 `.detach()`、转成 NumPy，或用 `torch.tensor(existing_tensor)` 重新包装，会切断原有梯度。这类处理由外部数据保存流程按需执行。模型训练入口保留梯度，采样时是否关闭梯度由调用方决定。

当前实现不会自动跳过等待出发或已完成列车。独立 Critic 按模型字典调用，共享 Critic 按观测字典调用，中央 Critic 按模型定义输出。采样与训练模块根据状态管理有效样本。

## 7. 后续怎样接入 GAE 和 PPO

以下是后续训练适配的约定，当前 `src/agent/critic.py` 只提供价值计算接口。逐列车模式按统一编号顺序把价值字典整理成形状为“列车数量 × 1”的张量；团队模式保留一个团队价值。保存多步数据后，再添加时间和环境批次维度。

| 训练组件 | 使用的数据 | 职责 |
|---|---|---|
| GAE 或其他优势计算组件 | 当前与下一状态价值、奖励、结束标记 | 计算动作表现相对预期的优势，以及训练价值模型的目标 |
| Critic loss | 当前模型重新预测的价值、价值目标 | 计算预测误差 |
| PPO 策略损失 | 动作新旧概率、优势 | 更新 Actor |

逐列车模式使用对应列车的奖励与结束信息计算目标。团队模式先明确团队奖励及团队结束规则，再计算团队价值目标和优势。团队奖励如何汇总、优势如何用于各列车动作，在训练配置和适配模块中约定。

TorchRL 使用 TensorDict 组织训练数据，常用字段包括 `state_value`、`advantage` 和 `value_target`。我们的价值字典通过适配层整理后接入这些字段，后续可以复用 TorchRL 的 GAE 和 PPO 价值损失。

采样时保存当前与下一步的观测、官方辅助信息、额外信息和价值估计。更新 Critic 时，用保存的输入重新运行当前模型，再与价值目标比较。可变数据保存独立副本，确保后续环境推进和额外信息更新保留历史值。

相关资料见 [TorchRL GAE](https://docs.pytorch.org/rl/0.9/reference/generated/torchrl.objectives.value.GAE.html) 和 [TorchRL PPO loss](https://docs.pytorch.org/rl/0.9/reference/generated/torchrl.objectives.ClipPPOLoss.html)。

# Critic and Core Model Interface Specification

This document describes the common interface in `src/agent/critic.py`, focusing on the core models used by each Critic class. A Critic estimates future cumulative return from the inputs at one step. The model reads fields and computes values. Training components will compute advantages, targets, losses, and parameter updates.

## 1. Critic Outputs

The current PPO framework uses a state value, written as `V`: the estimated cumulative reward obtained by continuing from the current situation under the policy. Each train receives one value. A centralized Critic can also produce a single value for the entire team.

| Output mode | Format | Meaning |
|---|---|---|
| Per-train values | `dict[int, Tensor]` | Each integer train ID maps to a floating-point tensor of shape `(1,)` |
| Team value | `Tensor` of shape `(1,)` | Expected cumulative return for the entire team |

Values may be positive, zero, or negative, depending on the reward function. The Actor produces five action scores per train, and the Critic produces one state value per train. They may use different models, parameter sharing arrangements, and information scopes.

## 2. Common Input Interface

Call all three Critics as follows:

```python
values = critic(
    observations,
    current_infos,
    additional_infos=additional_info,
)
```

| Parameter | Format | Content |
|---|---|---|
| `observations` | `dict[int, Any]` | Official observations for all trains at one step |
| `current_infos` | `dict[str, dict[int, Any]]` | Official info at the same step, accessed by category and then train ID |
| `additional_infos` | `dict[str, Any]` or `None` | Extra information supplied externally; defaults to `None` |

All three inputs describe the same time step. The external process reads or maintains maps, train positions, tasks, timetables, and progress, then places them in `additional_infos` according to the model's specification. The Critic forwards this information unchanged.

The Critic parameter is named `additional_infos`; the current Actor parameter is named `addtional_infos`. Use the parameter name defined by each class when calling it.

## 3. How the Three Critics Organize Models

| Critic | Construction | Model calls | Output |
|---|---|---|---|
| `IndependentCritic` | `IndependentCritic(models)` | Iterates over the train model dictionary and calls each train's own model | Per-train value dictionary |
| `ShareNetworkCritic` | `ShareNetworkCritic(model)` | Calls the same model separately for each train ID in the observation dictionary | Per-train value dictionary |
| `CentralizedCritic` | `CentralizedCritic(model, team_value=False)` | Calls the joint model once | Determined by `team_value` |

Core models inherit from `torch.nn.Module`. The base `Critic` initializes `model` to `None`, and subclasses assign concrete models. The base `forward` calls `_get_values` directly; subclasses implement model organization and invocation.

## 4. Independent and Shared Model Specification

### 4.1 Core Model Inputs

Both Critics use the same per-train model interface:

```python
model(
    observations,
    current_infos,
    additional_infos=additional_info,
    agent_id=agent_id,
)
```

The model entry point is:

```python
def forward(
    self,
    observations,
    current_infos,
    *,
    additional_infos=None,
    agent_id,
):
    ...
```

`agent_id` identifies the train whose value is being estimated. The model receives the complete dictionaries. Read the train's observation with `observations[agent_id]` and auxiliary data with expressions such as `current_infos["speed"][agent_id]`. Access to other trains or global data is agreed on by the model and experiment conditions.

### 4.2 Core Model Outputs

Each call returns a floating-point PyTorch tensor of shape `(1,)` with gradients retained. For example, `[5.0]` estimates that the train will obtain approximately 5 in cumulative return from the current time onward. Actual values come from network computation.

The Critic collects model outputs into a dictionary keyed by integer train IDs:

```python
import torch

values = {
    0: torch.tensor([5.0]),
    1: torch.tensor([8.0]),
}
```

This example illustrates the data format. Models return actual network outputs, keeping each value's shape as `(1,)` for consistent training tensor organization.

### 4.3 Model Construction

An independent Critic accepts a dictionary from integer IDs to models. Create a model instance for each train. Architectures may match, with parameters managed separately.

```python
from src.agent.critic import IndependentCritic

critic = IndependentCritic({
    0: TrainValueModel(...),
    1: TrainValueModel(...),
})
```

Models are registered internally in an `nn.ModuleDict`. Internal keys become strings, while input and output train IDs remain integers. PyTorch collects all model parameters through `critic.parameters()`.

A shared Critic accepts one model. All trains use the same parameters, and each value is computed with the relevant `agent_id`.

```python
from src.agent.critic import ShareNetworkCritic

critic = ShareNetworkCritic(TrainValueModel(...))
```

`TrainValueModel` represents the team's core model class, and `...` represents its constructor arguments. The current implementation calls the model once per train.

## 5. Centralized Critic and team_value

### 5.1 Core Model Inputs

The centralized Critic supplies all inputs to the model and forwards its constructor setting `team_value` as a keyword argument:

```python
model(
    observations,
    current_infos,
    additional_infos=additional_info,
    team_value=team_value,
)
```

The core model accepts this entry point:

```python
def forward(
    self,
    observations,
    current_infos,
    *,
    additional_infos=None,
    team_value=False,
):
    ...
```

The model selects its output mode using `team_value`. A model supporting both modes may include separate per-train and team outputs. If a model supports only one mode, document the available setting.

### 5.2 Two Output Modes

| Setting | Required model output | Prediction target |
|---|---|---|
| `team_value=False` | Dictionary from integer train IDs to floating-point tensors of shape `(1,)` | Future cumulative return for each train |
| `team_value=True` | One floating-point tensor of shape `(1,)` | Future cumulative return for the team |

The default is False. A centralized model may read global information and produce separate values for each train. In team mode, it produces one team value. Document output scope and information access in the model and experiment settings.

The centralized Critic checks the selected output mode: team mode requires a tensor of shape `(1,)`, and per-train mode requires a dictionary. The model supplies dictionary IDs, tensor shapes, and numeric values according to this specification.

### 5.3 Construction

```python
from src.agent.critic import CentralizedCritic

critic = CentralizedCritic(JointValueModel(...), team_value=False)
team_critic = CentralizedCritic(JointValueModel(...), team_value=True)
```

`JointValueModel` represents a core model that jointly processes the inputs. Each Critic call invokes that model once.

## 6. Common Model Requirements

| Item | Requirement |
|---|---|
| Output | Return finite floating-point tensors, with each individual value shaped `(1,)` |
| Gradients | Return network results directly and retain the computation from parameters to values |
| Device | Use compatible devices for inputs and parameters; callers can move models with `critic.to(device)` |
| Missing data | Handle observations that are `None`; document required extra inputs |
| Input documentation | Record required observation types, feature lengths, auxiliary fields, and additional information scope |
| Historical inputs | Compute from supplied data so that saved historical samples can be used for another forward pass during training |
| Output scope | Per-train outputs match train IDs; team output matches the team reward target |

Calling `.detach()`, converting results to NumPy, or wrapping them with `torch.tensor(existing_tensor)` disconnects the original gradients. External data storage may perform these operations when needed. Retain gradients at the model's training entry point. The caller decides whether to disable gradients during sampling.

The current implementation processes waiting and completed trains as well. The independent Critic uses its model dictionary, the shared Critic uses the observation dictionary, and the centralized Critic follows its model's output definition. Sampling and training components manage valid samples according to train states.

## 7. Connecting to GAE and PPO Later

The following conventions describe future training adaptation. Currently, `src/agent/critic.py` provides the value computation interface. In per-train mode, arrange the dictionary in a consistent train order into a tensor of shape “number of trains × 1”. In team mode, retain one team value. Add time and environment batch dimensions after collecting multiple steps.

| Training component | Inputs | Responsibility |
|---|---|---|
| GAE or another advantage estimator | Current and next state values, rewards, and end flags | Compute how an action performed relative to expectations and produce value training targets |
| Critic loss | Values recomputed by the current model and value targets | Compute prediction error |
| PPO policy loss | New and old action probabilities and advantages | Update the Actor |

Per-train mode uses each train's rewards and end flags to compute targets. Team mode requires a defined team reward and team ending rule before computing team value targets and advantages. Training configuration and adapters specify how to aggregate team rewards and apply advantages to train actions.

TorchRL organizes training data in TensorDicts. Common fields include `state_value`, `advantage`, and `value_target`. An adapter converts our value dictionaries into these fields so that later training can reuse TorchRL's GAE and PPO value loss.

During sampling, save current and next observations, official auxiliary information, additional information, and value estimates. When updating the Critic, run the current model again on saved inputs and compare predictions with value targets. Save independent copies of mutable data so that later environment steps and extra-information updates preserve historical values.

See [TorchRL GAE](https://docs.pytorch.org/rl/0.9/reference/generated/torchrl.objectives.value.GAE.html) and [TorchRL PPO loss](https://docs.pytorch.org/rl/0.9/reference/generated/torchrl.objectives.ClipPPOLoss.html).
