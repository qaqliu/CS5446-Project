# 每一步怎样输入动作、读取状态

[中文](#chinese) | [English](#english)

本文说明 Flatland 4.3.0 中每次环境交互的数据格式。项目的观测和 `info` 使用官方现成组件与字段。当前实验关闭故障生成，已有故障字段保留官方格式；项目范围见 [实验设置](../setting/1.experiment_variable.md)。阅读顺序是：先了解动作怎样交给环境，再了解环境返回的观测、辅助信息、奖励和结束标记。创建环境和运行完整一局的方法见 [Flatland 使用教程](1.flatland_overview.md)。

## 1. 先认识每一步的输入和输出

在 Flatland 中，一列车对应一个智能体。环境用整数给列车编号，例如两列车的编号为 0 和 1。源码把这个编号称为 `handle`；本文的代码使用 `train_id`，两者都表示列车编号。`env` 是创建好的铁路环境对象，`env.get_agent_handles()` 可以取得其中全部列车的编号。

开始一局时调用 `reset()`。随后，每次调用 `step()`，把全部需要控制的列车动作一起交给环境。环境推进一个时间步，再返回更新后的数据。列车是否移动取决于轨道、速度、出发时间、故障和其他列车占用情况。例如，处于等待出发状态的列车可以在这一步保持原位。

```python
# Start an episode and obtain initial observations and auxiliary information.
observations, info = env.reset()

# Request forward movement for train 0 and stopping for train 1.
actions = {0: 2, 1: 4}

# Advance one time step and receive four results.
next_observations, rewards, dones, next_info = env.step(actions)
```

| 变量 | 保存的内容 | 读取示例 |
|---|---|---|
| `actions` | 每列车要执行的动作 | `actions[0]` 是给列车 0 的动作 |
| `next_observations` | 每列车在这一步之后获得的观测 | `next_observations[0]` 是列车 0 的观测 |
| `rewards` | 每列车在这一步获得的奖励 | `rewards[0]` 是列车 0 的本步奖励 |
| `dones` | 每列车和整局的结束标记 | `dones[0]` 查看列车 0，`dones["__all__"]` 查看整局 |
| `next_info` | 更新后的列车运行辅助信息 | `next_info["speed"][0]` 查看列车 0 的速度 |

前缀 `next_` 表示“动作执行之后”。下一轮选择动作时，使用 `next_observations` 和 `next_info`。Python 的 `True` 表示条件成立，`False` 表示条件尚未成立；这两种值经常用于结束标记和动作需求提示。

## 2. 动作输入：列车编号对应一个动作

### 2.1 用字典提交动作

动作字典的键是列车编号，值是动作编号。下面的 `{0: 2, 1: 4}` 表示列车 0 前进、列车 1 停车。可以使用动作枚举，让代码中的动作名称更容易阅读；枚举是给固定编号起的一组名称。

```python
from flatland.envs.rail_env_action import RailEnvActions

# Use integer IDs.
actions = {0: 2, 1: 4}

# Use names for the same actions.
actions = {
    0: RailEnvActions.MOVE_FORWARD,
    1: RailEnvActions.STOP_MOVING,
}
```

如果策略网络先输出五个动作的分数或概率，先从中选出一个动作，再将对应的整数编号写入字典。提交前检查每个动作在 0 到 4 的范围内。环境会给未出现在字典中的列车使用动作 0，因此 `actions = {0: 2}` 表示给列车 0 前进指令，其他列车使用 `DO_NOTHING`。

### 2.2 五种动作怎样使用

| 编号 | 动作名称 | 使用方法 |
|---|---|---|
| 0 | `DO_NOTHING` | 保持当前运动控制：行驶中的列车通常继续走，停止的列车通常继续停 |
| 1 | `MOVE_LEFT` | 在有左侧出口的轨道分支处选择左路 |
| 2 | `MOVE_FORWARD` | 请求前进，在允许加速的情况下提高速度 |
| 3 | `MOVE_RIGHT` | 在有右侧出口的轨道分支处选择右路 |
| 4 | `STOP_MOVING` | 请求制动，直到停车；默认制动设置下通常可以立即停下 |

左和右以列车当前朝向为参照。例如列车朝北时，左侧是西；朝东时，左侧是北。弯道或尽头只有一条出口时，环境会按轨道规则处理方向。选择停车时使用动作 4；动作 0 用于保持当前控制。想观察某动作的实际效果，可以同时比较动作前后的列车位置和运行状态。

### 2.3 怎样读取动作需求提示

通过 `info["action_required"][train_id]` 查看某列车当前是否被环境标记为需要动作。下面的代码为这些列车提交前进指令，其他列车使用默认动作 0。

```python
actions = {}
for train_id in env.get_agent_handles():
    if info["action_required"][train_id]:
        actions[train_id] = RailEnvActions.MOVE_FORWARD
```

这个标记综合了列车是否准备出发、是否处于地图内状态以及是否处于相应轨道格边界等条件。采样器读取当前的 `action_required` 管理决策时刻，同时计算下面的动作掩码管理允许选择的动作。每步是否选择动作、哪些动作允许选择，分别保存。第一版需要结合加速、制动和故障过程验证这两项处理。

### 2.4 第一版直接使用动作掩码

第一版在 actor 选择动作时启用动作掩码。动作掩码是一组按五个动作编号排列的布尔值，True 表示允许选择，False 表示屏蔽。例如 `[True, False, True, False, True]` 表示允许保持当前控制、前进和停车，屏蔽左转与右转。每列车计算自己的掩码，每次决策前根据当前环境重新计算。

掩码由项目的动作选择模块计算。该模块读取官方环境中的轨道连接、列车位置、朝向、运行状态和动作需求提示，观测与 info 继续使用官方字段。掩码作为独立的动作选择数据保存到训练记录中。

| 读取的信息 | 用途 |
|---|---|
| `env.agents[train_id].current_configuration` | 获取地图内列车当前位置和朝向 |
| `env.agents[train_id].initial_configuration` | 获取准备出发列车的起点和朝向 |
| `env.rail.get_transitions(configuration)` | 获取当前轨道配置允许的出口方向；configuration 表示位置与方向的组合，具体格式见第 4.3 节 |
| `info["state"][train_id]` | 处理等待、出发、行驶、停车、故障和完成状态 |
| `info["malfunction"][train_id]` | 配合运行状态处理故障过程 |
| `info["action_required"][train_id]` | 判断本步是否安排一次策略决策 |

第一版按轨道和动作本身的执行规则屏蔽无效选择。将列车的左、前、右请求与轨道允许出口比较，屏蔽需要环境改成其他运动指令的选择。弯道和尽头的前进动作按 Flatland 官方语义保留；保持当前控制和停车动作按运行状态判断。这样列车可以沿单一路径前进，也可以在需要选择路线时明确选择可行分支。

等待、故障、已完成及当前无需策略决策的列车，由采样器按状态提交必要的默认控制，并将该步标记为无需策略决策。所有掩码都要保留至少一个可用控制。第一版允许列车面对暂时被占用的轨道等待，占用处理沿用环境的资源检查；掩码先负责轨道与动作合法性。

Actor 输出五个动作分数后，动作分布将被屏蔽动作的概率设为零，再从允许动作中采样。保存动作时，同时保存当时的掩码和该动作的对数概率。对数概率是动作概率取自然对数后的数值，PPO 用它比较采样时与更新后的策略。PPO 更新时用同一份历史掩码重新计算动作概率，确保采样和训练使用相同的允许动作集合。

整个顺序为：读取当前环境和官方 info → 计算本步掩码 → actor 输出动作分数 → 按掩码建立动作分布 → 采样动作 → 提交动作字典 → 保存本步数据。

## 3. 观测输出：先按列车编号取出数据

### 3.1 怎样选择观测类型

创建环境时，通过 `obs_builder_object` 选择观测生成器。观测生成器负责把环境信息整理成列车能读取的数据。本文介绍树观测、全局观测，以及官方展平和归一化后的树观测，具体使用代码见第 7 节。

| 观测生成器 | 每列车得到的数据 | 阅读方式 |
|---|---|---|
| `TreeObsForRailEnv` | 一棵沿轨道展开的树 | 读取树节点字段和子分支 |
| `GlobalObsForRailEnv` | 三个数组 | 分别读取轨道、列车和目标信息 |
| `FlattenedTreeObsForRailEnv` | 一维数组 | 使用官方展平后的树特征 |
| `FlattenedNormalizedTreeObsForRailEnv` | 一维数组 | 使用官方展平并缩放后的树特征 |

调用 `reset()` 和 `step()` 后，先用列车编号取得自己的观测，例如 `observations[0]`。变量名称 `observations` 可以简写为官方示例中的 `obs`。直接创建 `RailEnv` 时默认使用全局观测；本文和使用教程中的示例显式选择树观测。

某些情况下观测值可能为 `None`，它在 Python 中表示当前没有可用观测对象。读取字段前先检查这个值。判断列车是否到站时使用第 4 节的运行状态，因为树观测在等待和到站之后仍可能提供有效数据。

### 3.2 树观测：沿轨道查看后续情况

树观测从当前列车所在位置开始，沿轨道向前探索。每遇到一个分支，就继续记录各条路线上的目标、其他列车、故障和距离信息。每一条探索出来的轨道段用一个 `Node` 对象表示；`Node` 是保存固定名称字段的 Python 对象。起始的节点叫根节点，沿分支继续探索得到的节点叫子节点。

`TreeObsForRailEnv(max_depth=2)` 中的 `max_depth` 表示探索到多少层分支。深度 2 表示保留根节点及后续两层分支。在四个方向都展开的情况下，共有一个根节点、四个第一层节点、十六个第二层节点，最多 21 个节点。实际树大小取决于轨道连接。

```python
# observations comes from an environment using tree observations.
train_id = 0
root = observations[train_id]

if root is not None:
    print("到目标的最短距离：", root.dist_min_to_target)
    print("自身故障剩余计数：", root.num_agents_malfunctioning)
    print("自身速度：", float(root.speed_min_fractional))
```

每个节点有下面 12 个数值字段，另外还有保存子分支的 `childs` 字段。距离按轨道格数计算；各字段在根节点和沿途节点的解释见表格及随后说明。

| 字段 | 读取后可以了解什么 |
|---|---|
| `dist_own_target_encountered` | 沿这条路线走多远会遇到自己的目标 |
| `dist_other_target_encountered` | 沿这条路线走多远会遇到其他列车的目标 |
| `dist_other_agent_encountered` | 沿这条路线走多远会遇到其他列车 |
| `dist_potential_conflict` | 预测可能发生路线冲突的位置距离 |
| `dist_unusable_switch` | 沿途无法按当前方向使用的道岔距离 |
| `dist_to_next_branch` | 到下一个分支点或本段终点的距离 |
| `dist_min_to_target` | 这段轨道对应的最短目标距离信息 |
| `num_agents_same_direction` | 沿途同方向列车数量 |
| `num_agents_opposite_direction` | 沿途反方向列车数量 |
| `num_agents_malfunctioning` | 沿途故障列车数量；根节点保存自身故障剩余计数 |
| `speed_min_fractional` | 沿途同向列车的最低速度信息；根节点保存自身速度 |
| `num_agents_ready_to_depart` | 沿途准备出发的列车数量 |

根节点的重点字段是自身最短目标距离、故障计数和速度，其余若干字段初始化为 0。读取分支节点时，再按沿途信息解释这些字段。例如根节点的 `num_agents_malfunctioning` 为 8，表示自身还有 8 个故障计时单位；分支节点的同名字段为 2，表示该分支记录了两列故障列车。

#### 读取子分支

`childs` 是一个字典，使用 `L`、`F`、`R`、`B` 四个标签保存左、前、右、后分支。标签来自英文 Left、Forward、Right、Back。单一出口的轨道会按该出口调整树的朝向，因此读取时结合轨道结构理解标签。

```python
from flatland.envs.observations import Node

if root is not None:
    forward_branch = root.childs.get("F")
    if isinstance(forward_branch, Node):
        print("前方分支中的其他列车数量：",
              forward_branch.num_agents_same_direction)
```

字典的 `.get("F")` 用于安全读取前方分支；键不存在时返回 `None`。环境还会用负无穷表示缺失分支，Python 中通常写成 `-np.inf`，其中 `np` 是 NumPy 库的常用别名，`inf` 表示无穷。`isinstance(value, Node)` 用来检查取出的值是否为真实节点。节点中的正无穷也可能表示探索范围内没有找到相应目标或事件。向神经网络提供树观测时，使用第 3.4 节的官方归一化展平组件处理这些值。

4.3.0 的 `Node` 包含 12 个数值字段，而类的 `observation_dim` 属性仍写着 11。读取树节点时按实际字段理解内容。使用官方展平组件时，通过 `get_len_flattened()` 取得输入长度；深度 2 对应 252 个数值。

#### 使用冲突预测

创建树观测时可以传入 `ShortestPathPredictorForRailEnv`。这个预测器假设列车沿最短路径行驶，据此估计未来可能相遇的位置。`max_depth=20` 表示向后续 20 个预测时间步查看。使用潜在冲突字段时，在实验配置中记录预测器及其预测长度，并结合实际策略表现评估预测效果。

```python
from flatland.envs.observations import TreeObsForRailEnv
from flatland.envs.predictions import ShortestPathPredictorForRailEnv

tree_builder = TreeObsForRailEnv(
    max_depth=2,
    predictor=ShortestPathPredictorForRailEnv(max_depth=20),
)
```

### 3.3 全局观测：读取整张地图的三个数组

全局观测为每列车返回三个 NumPy 数组。数组按“地图行、地图列、信息通道”排列。信息通道可以理解为同一张地图上的不同数据层，例如一层保存方向，一层保存故障。下面以高 30 格、宽 30 格的地图说明。

```python
# observations comes from an environment using GlobalObsForRailEnv.
rail_map, train_map, target_map = observations[0]

print(rail_map.shape)    # (30, 30, 16)
print(train_map.shape)   # (30, 30, 5)
print(target_map.shape)  # (30, 30, 2)
```

`.shape` 表示数组各个维度的长度。例如 `(30, 30, 5)` 表示 30 行、30 列，每格保存 5 个数值。地图尺寸改变时，前两个长度随之改变；通道数量保持不变。当前实现的数组元素类型为 `float64`，即 64 位浮点数，训练前可统一转换成 `float32`，即 32 位浮点数。

#### 轨道数组 rail_map

每格有 16 个轨道连接标记，描述列车从不同朝向进入该格后能够从哪些方向离开。四个进入朝向和四个离开方向构成 16 种组合。它们来自环境的轨道转换编码；需要查看某列车当前位置的可行出口时，直接使用教程中的 `get_transitions()` 查询方法。

#### 列车数组 train_map

| 通道编号 | 内容 |
|---|---|
| 0 | 当前列车的参考位置和方向 |
| 1 | 其他尚未完成、位于地图内的列车位置和方向 |
| 2 | 地图内列车的故障剩余计数 |
| 3 | 地图内列车的速度 |
| 4 | 以该格为起点、当前仍处于地图外的列车数量 |

通道 0 在列车等待出发时可以使用起点，在完成后可以使用目标位置。通道 0 和 1 的数值 0、1、2、3 分别表示北、东、南、西；未填写的格子通常使用 -1。故障和速度通道也通常以 -1 表示未填写的位置，地图外列车数量通道则以 0 开始计数。读取第三行、第七列的故障值可以写成 `train_map[3, 7, 2]`；Python 的行列索引从 0 开始，因此索引 3 对应地图中的第 4 行。

#### 目标数组 target_map

通道 0 标记当前列车的目标位置，通道 1 标记未完成列车的目标位置。目标格写 1，其余格写 0。4.3.0 在填写通道 1 时也会遍历当前列车，所以其中可能包含自身目标。列车允许多个目标位置时，当前全局观测选取 `targets` 集合中的一个配置进行标记；需要全部备选终点时读取列车对象的 `targets`。

每列车的全局观测都以自身为参照，所以列车 0 和列车 1 的通道 0 内容会不同。时间表和途经站等更完整任务信息，可按第 4.3 节从列车对象读取。

### 3.4 官方展平后的树观测：直接取得数值向量

这组官方组件依赖 Ray RLlib，Ray 是并行计算库，RLlib 是其中的强化学习模块。项目的 `environment.yml` 已包含 Ray 2.58.0 及 RLlib 依赖。已有环境需要同步依赖时，在仓库根目录运行下面的命令。

```bash
conda env update -n cs5446-project -f environment.yml
```

使用 `FlattenedTreeObsForRailEnv` 可以让环境直接返回固定长度的一维数组。使用 `FlattenedNormalizedTreeObsForRailEnv` 可以进一步让官方组件完成数值缩放和裁剪。这里“展平”表示把树中的特征排成一条数组，“归一化”表示将数值缩放到适合处理的范围。项目直接选择这些现成组件。

```python
from flatland.ml.observations.flatten_tree_observation_for_rail_env import (
    FlattenedNormalizedTreeObsForRailEnv,
)

observation_builder = FlattenedNormalizedTreeObsForRailEnv(
    max_depth=2,
    observation_radius=2,
)
# Pass this object as obs_builder_object when creating the environment in Section 7.
```

设置 `max_depth=2` 后，每列车的观测形状为 `(252,)`，表示一维数组中有 252 个数。这个长度来自 21 个树节点和每节点 12 个特征。`observation_radius=2` 用于距离特征的缩放，探索到几层轨道分支仍由 `max_depth` 控制。数组默认使用 64 位浮点数，传给策略网络时可转成 32 位浮点数。

官方组件按三组特征排列数组：先是六类沿途距离，再是最短目标距离，最后是五类列车信息。深度 2 时，三组分别包含 126、21、105 个数。归一化版本按官方规则缩放和裁剪特征，原始故障计数通过 `info["malfunction"][train_id]` 读取。策略输入保持官方输出，转换成张量时保持原有的特征顺序。

## 4. 辅助信息 info：查看全部列车的运行情况

### 4.1 按信息类别，再按列车编号读取

`info` 包含全部列车的四类辅助信息。先写信息类别，再写列车编号。例如 `info["malfunction"][1]` 表示查看列车 1 的故障剩余计数。下面给出一个完整的数据格式例子，数值用于说明读取方法。

```python
from fractions import Fraction
from flatland.envs.step_utils.states import TrainState

info_example = {
    "action_required": {0: True, 1: False},
    "malfunction": {0: 0, 1: 8},
    "speed": {0: Fraction(1, 1), 1: Fraction(1, 2)},
    "state": {0: TrainState.MOVING, 1: TrainState.MALFUNCTION},
}

print(info_example["malfunction"][1])   # 8
print(float(info_example["speed"][1]))  # 0.5
```

`Fraction(1, 2)` 是 Python 用分数表示的二分之一，调用 `float()` 后得到浮点数 0.5。故障期间速度计可能保留原速度；判断列车这一刻的运行情况时，同时查看运行状态和位置变化。

| 信息类别 | 值的含义 | 推荐读取方式 |
|---|---|---|
| `action_required` | 是否被环境标记为需要动作 | 按列车读取 True／False |
| `malfunction` | 故障剩余计数 | 正数表示仍有故障计时 |
| `speed` | 速度计当前值 | 转成浮点数后用于展示或张量处理 |
| `state` | 列车的运行状态 | 与下面的 `TrainState` 名称比较 |

### 4.2 运行状态怎样判断

| 状态编号 | 名称 | 解释 |
|---|---|---|
| 0 | `WAITING` | 等待满足出发时间条件 |
| 1 | `READY_TO_DEPART` | 已准备好出发 |
| 2 | `MALFUNCTION_OFF_MAP` | 进入地图前发生故障 |
| 3 | `MOVING` | 处于行驶状态 |
| 4 | `STOPPED` | 已进入地图并处于停车状态 |
| 5 | `MALFUNCTION` | 地图内故障 |
| 6 | `DONE` | 已完成目标任务 |

代码中直接使用名称比较，便于阅读。例如 `info["state"][0] == TrainState.DONE` 表示判断列车 0 是否真正完成任务。故障计数会在环境更新过程中减少，状态机也有自己的更新时间；边界步可能出现计数已经为 0、状态仍为故障的情况，处理时优先按运行状态解释。

### 4.3 读取地图、任务和时间表

默认 `info` 提供上述四项信息。需要更完整的全局信息时，从环境对象及其列车对象读取。下面的 `agent` 表示列车 0 的对象，保存它的任务和当前运行数据。

```python
agent = env.agents[0]
print("起点：", agent.initial_configuration)
print("当前位置：", agent.current_configuration)
print("可接受的目标：", agent.targets)
print("最早出发时间：", agent.earliest_departure)
print("最晚到达时间：", agent.latest_arrival)
```

位置和方向组合使用 `((row, column), direction)` 格式，其中 `row` 是从 0 开始的行索引，`column` 是从 0 开始的列索引，`direction` 是方向编号。例如 `((3, 7), 1)` 表示第 4 行、第 8 列，朝东。`current_configuration` 在列车尚未进入地图或到站移除后可能为 `None`，取位置前先检查。

| 信息 | 读取位置 |
|---|---|
| 起始位置和方向 | `agent.initial_configuration` |
| 当前所在位置和方向 | `agent.current_configuration` |
| 全部可接受终点配置 | `agent.targets`，一个配置集合 |
| 实际到达的终点配置 | `agent.target_configuration` |
| 最早出发时间 | `agent.earliest_departure` |
| 最晚到达时间 | `agent.latest_arrival` |
| 实际到达时间 | `agent.arrival_time`，未到站时为 None |
| 途经站和时间要求 | `agent.waypoints`、`waypoints_earliest_departure`、`waypoints_latest_arrival` |
| 轨道地图 | `env.rail.grid` |
| 各位置到目标的最短距离 | `env.distance_map.get()` |
| 已经过的时间步数 | `env._elapsed_steps` |
| 本局最多允许的时间步数 | `env._max_episode_steps` |

最后两个名称以 `_` 开头，表示库的内部字段。项目后续可将时间读取集中放在环境适配代码中，其他模块通过项目接口取得时间。死锁和冲突统计也由项目另行定义与计算，例如记录连续等待时间、相互阻塞的列车关系或被环境阻止的移动。

## 5. 奖励和结束标记怎样读取

`rewards[train_id]` 保存本次环境更新产生的奖励。默认奖励通常在普通步骤为 0，在延误、未完成等情况下给出负值。累计整局回报时，为每列车建立一个总和，每次 step 后加上本步奖励。

`dones[train_id]` 查看某列车的结束标记，`dones["__all__"]` 查看整局是否结束。某列车提前到站后，其他列车可以继续运行；整局结束后退出循环，开始下一局时调用 reset。

```python
if dones["__all__"]:
    print("本局已经结束")
```

环境达到时间上限时，会把所有列车的结束标记设为 True。计算完成率时，统计运行状态为 `TrainState.DONE` 的列车，再除以列车总数。例如两列车中只有一列到站，完成率就是 0.5。训练时另外记录“全部到站”和“达到时间上限”这两种结束原因，供计算后续价值目标时使用。

## 6. 保存一轮训练数据时保留什么

一轮数据至少记录动作之前的观测、动作掩码、动作、该动作的对数概率、奖励、动作之后的观测，以及结束标记。辅助信息也分动作之前和之后保存，这样可以追踪列车何时需要决策、何时发生故障、何时到站。无需策略决策的步骤使用单独的决策标记，策略更新时按该标记筛选样本。记录动作需求提示时，读取用于选择当前动作的那份 info。

环境字典和树对象可能被后续更新影响。采样器保存历史记录时复制需要的数据，或者立即转换成独立数组／张量。神经网络输入采用所选官方观测的形状，采样器按一致的列车顺序保存这些数据。

## 7. 完整示例：打印一次交互结果

激活 `cs5446-project` 环境后运行下面的代码。它创建两列车环境，打印初始信息，再给每列车提交前进动作并打印结果。这个示例用于检查官方环境的数据格式；第一版 PPO 的动作选择按第 2.4 节加入掩码。若要检查全局观测，将 `observation_builder` 赋值为 `GlobalObsForRailEnv()`；若要检查官方处理后的向量观测，使用第 3.4 节的归一化展平组件。

```python
from flatland.envs.rail_env import RailEnv
from flatland.envs.rail_env_action import RailEnvActions
from flatland.envs.rail_generators import sparse_rail_generator
from flatland.envs.line_generators import sparse_line_generator
from flatland.envs.observations import (
    TreeObsForRailEnv, GlobalObsForRailEnv, Node,
)

observation_builder = TreeObsForRailEnv(max_depth=2)
env = RailEnv(
    width=30,
    height=30,
    number_of_agents=2,
    rail_generator=sparse_rail_generator(max_num_cities=2, grid_mode=True),
    line_generator=sparse_line_generator(),
    obs_builder_object=observation_builder,
    random_seed=42,
)

observations, info = env.reset(random_seed=42)
print("初始运行信息：", info)

actions = {}
for train_id in env.get_agent_handles():
    actions[train_id] = RailEnvActions.MOVE_FORWARD

next_observations, rewards, dones, next_info = env.step(actions)
print("提交动作：", actions)
print("本步奖励：", rewards)
print("结束标记：", dones)
print("更新后运行信息：", next_info)

for train_id, observation in next_observations.items():
    if observation is None:
        print("列车", train_id, "当前观测为空")
    elif isinstance(observation, Node):
        print("列车", train_id, "树节点字段：", observation._fields)
        print("可读取的子分支：", list(observation.childs.keys()))
    elif isinstance(observation, tuple):
        rail_map, train_map, target_map = observation
        print("列车", train_id, "数组形状：",
              rail_map.shape, train_map.shape, target_map.shape)
    else:
        print("列车", train_id, "向量形状：", observation.shape)
```

# Providing Actions and Reading State at Each Step

This document explains the data formats used in each Flatland 4.3.0 interaction. The project uses official observation components and `info` fields. Current experiments disable malfunction generation while retaining existing malfunction fields in their official format. See [experiment settings](../setting/1.experiment_variable.md) for the scope. Read actions first, followed by returned observations, auxiliary information, rewards, and end flags. See [the Flatland tutorial](1.flatland_overview.md) for environment creation and complete episodes.

## 1. Inputs and Outputs of a Step

In Flatland, each train is an agent. The environment assigns integer train IDs; two trains might have IDs 0 and 1. The source calls this ID a `handle`; examples here use `train_id`. Both refer to the train ID. `env` is the railway environment object, and `env.get_agent_handles()` returns all its train IDs.

Call `reset()` to start an episode. Then each `step()` submits actions together for all trains being controlled. The environment advances one time step and returns updated data. Movement depends on tracks, speed, departure time, malfunctions, and other trains' occupancy. A train waiting to depart may remain in place during the step.

```python
# Start an episode and obtain initial observations and auxiliary information.
observations, info = env.reset()

# Request forward movement for train 0 and stopping for train 1.
actions = {0: 2, 1: 4}

# Advance one time step and receive four results.
next_observations, rewards, dones, next_info = env.step(actions)
```

| Variable | Content | Access example |
|---|---|---|
| `actions` | Action for each train | `actions[0]` is train 0's action |
| `next_observations` | Observation each train receives after this step | `next_observations[0]` is train 0's observation |
| `rewards` | Reward each train receives at this step | `rewards[0]` is train 0's step reward |
| `dones` | End flags for each train and the episode | `dones[0]` checks train 0; `dones["__all__"]` checks the episode |
| `next_info` | Updated train running information | `next_info["speed"][0]` reads train 0's speed |

The prefix `next_` means after the action. Use `next_observations` and `next_info` for the next decision. Python's `True` means a condition holds, and `False` means it does not yet hold. These values commonly appear in end flags and action requirement indicators.

## 2. Action Inputs: One Action per Train ID

### 2.1 Submit Actions in a Dictionary

Action dictionary keys are train IDs, and values are action IDs. `{0: 2, 1: 4}` requests forward movement for train 0 and stopping for train 1. Use action enums to make names easier to read; an enum assigns names to a fixed set of IDs.

```python
from flatland.envs.rail_env_action import RailEnvActions

# Use integer IDs.
actions = {0: 2, 1: 4}

# Use names for the same actions.
actions = {
    0: RailEnvActions.MOVE_FORWARD,
    1: RailEnvActions.STOP_MOVING,
}
```

If the policy network produces scores or probabilities for five actions, select one first and write its integer ID into the dictionary. Check that every action lies between 0 and 4 before submission. Omitted trains receive action 0. Thus `actions = {0: 2}` requests forward movement for train 0 and `DO_NOTHING` for the others.

### 2.2 Using the Five Actions

| ID | Action name | Usage |
|---|---|---|
| 0 | `DO_NOTHING` | Retain current movement control: moving trains generally continue, and stopped trains generally remain stopped |
| 1 | `MOVE_LEFT` | Choose the left route at a track branch with a left exit |
| 2 | `MOVE_FORWARD` | Request forward movement and increase speed when acceleration is allowed |
| 3 | `MOVE_RIGHT` | Choose the right route at a track branch with a right exit |
| 4 | `STOP_MOVING` | Request braking until stopped; default braking usually allows an immediate stop |

Left and right are relative to current orientation. Facing north, left is west; facing east, left is north. At a curve or dead end with one exit, the environment handles direction according to track rules. Use action 4 to stop and action 0 to retain control. Compare positions and running states before and after actions to inspect their actual effects.

### 2.3 Reading the Action Requirement Indicator

`info["action_required"][train_id]` reports whether the environment currently marks a train as needing an action. This example submits forward actions for those trains; the others receive default action 0.

```python
actions = {}
for train_id in env.get_agent_handles():
    if info["action_required"][train_id]:
        actions[train_id] = RailEnvActions.MOVE_FORWARD
```

The flag incorporates conditions such as readiness to depart, on-map state, and relevant track-cell boundaries. The sampler uses current `action_required` to manage decision times and the action mask below to manage allowed choices. Save whether a policy decision occurred and which actions were allowed separately. The first version needs to validate both treatments together with acceleration, braking, and malfunction processes.

### 2.4 Enable Action Masks in the First Version

Enable action masks when the Actor selects actions in the first version. A mask contains five Boolean values in action-ID order: True allows selection, and False blocks it. For example, `[True, False, True, False, True]` permits retaining control, moving forward, and stopping, while blocking left and right. Compute a separate mask for each train and refresh it from the current environment before every decision.

The project's action selection module computes masks using official track connections, positions, orientations, running states, and action requirement indicators. Observations and info retain official fields. Save masks separately in training records as action selection data.

| Information read | Purpose |
|---|---|
| `env.agents[train_id].current_configuration` | Current on-map position and orientation |
| `env.agents[train_id].initial_configuration` | Origin position and orientation for a train preparing to depart |
| `env.rail.get_transitions(configuration)` | Allowed exits at the current track configuration; configuration combines position and direction, as explained in Section 4.3 |
| `info["state"][train_id]` | Handle waiting, departure, movement, stopping, malfunction, and completion states |
| `info["malfunction"][train_id]` | Handle malfunction processes together with the running state |
| `info["action_required"][train_id]` | Determine whether to arrange a policy decision this step |

The first version blocks invalid choices according to tracks and action execution rules. Compare left, forward, and right requests with allowed track exits and block choices that require the environment to substitute a different movement instruction. Retain forward actions at curves and dead ends according to official Flatland semantics. Determine retaining control and stopping from the running state. This allows following a single route and explicitly selecting valid branches when route choices are needed.

For waiting, malfunctioning, completed, or currently non-decision trains, the sampler submits necessary default controls according to state and marks the step as requiring no policy decision. Every mask must retain at least one available control. The first version allows trains to wait in front of temporarily occupied tracks. Occupancy uses the environment's resource checks, while masks handle track and action validity first.

After the Actor produces five scores, the action distribution assigns zero probability to masked actions and samples from allowed choices. Save the mask and the selected action's log probability together with the action. A log probability is the natural logarithm of the action probability; PPO uses it to compare the sampling policy with the updated policy. Recompute probabilities with the same historical mask during PPO updates to keep sampling and training action sets consistent.

The sequence is: read the current environment and official info → compute the mask → obtain Actor scores → build a masked distribution → sample actions → submit the action dictionary → save step data.

## 3. Observation Outputs: Retrieve Data by Train ID

### 3.1 Choosing an Observation Type

Select the builder through `obs_builder_object` when creating the environment. It organizes environment information into data available to trains. This document covers tree, global, and officially flattened/normalized tree observations. Section 7 shows usage.

| Observation builder | Data per train | How to read it |
|---|---|---|
| `TreeObsForRailEnv` | Tree expanded along tracks | Read node fields and child branches |
| `GlobalObsForRailEnv` | Three arrays | Read track, train, and target information separately |
| `FlattenedTreeObsForRailEnv` | One-dimensional array | Use officially flattened tree features |
| `FlattenedNormalizedTreeObsForRailEnv` | One-dimensional array | Use officially flattened and scaled tree features |

After `reset()` or `step()`, retrieve observations by train ID, for example `observations[0]`. Official examples sometimes shorten the name to `obs`. Creating `RailEnv` directly uses global observations by default. Examples here and in the tutorial explicitly choose tree observations.

An observation can be `None`, meaning no observation object is currently available. Check before reading fields. Use the running states in Section 4 to determine arrivals; tree observations may remain valid while waiting and after arrival.

### 3.2 Tree Observations: Exploring Upcoming Tracks

Tree observations begin at the observing train's position and explore tracks ahead. At each branch, they continue recording targets, other trains, malfunctions, and distances along possible routes. Each explored track segment is represented by a `Node`, a Python object with fixed named fields. The starting node is the root; nodes found farther along branches are child nodes.

In `TreeObsForRailEnv(max_depth=2)`, `max_depth` controls the number of branch levels explored. Depth 2 keeps the root and two following levels. With all four branches expanded, there are one root, four first-level nodes, and sixteen second-level nodes: up to 21 in total. Actual tree size depends on track connections.

```python
# observations comes from an environment using tree observations.
train_id = 0
root = observations[train_id]

if root is not None:
    print("Shortest distance to target:", root.dist_min_to_target)
    print("Own remaining malfunction counter:", root.num_agents_malfunctioning)
    print("Own speed:", float(root.speed_min_fractional))
```

Each node has the following 12 numeric fields and a `childs` field for child branches. Distances are in track cells. The table and notes explain root and branch interpretations.

| Field | Information |
|---|---|
| `dist_own_target_encountered` | Distance along the route to the observing train's target |
| `dist_other_target_encountered` | Distance along the route to another train's target |
| `dist_other_agent_encountered` | Distance along the route to another train |
| `dist_potential_conflict` | Distance to a predicted potential route conflict |
| `dist_unusable_switch` | Distance to a switch unusable from the current direction |
| `dist_to_next_branch` | Distance to the next branch or end of the segment |
| `dist_min_to_target` | Shortest target-distance information for this track segment |
| `num_agents_same_direction` | Number of trains facing the same direction along the segment |
| `num_agents_opposite_direction` | Number of trains facing the opposite direction |
| `num_agents_malfunctioning` | Number of malfunctioning trains along the segment; the root stores the observing train's remaining malfunction counter |
| `speed_min_fractional` | Minimum speed information for same-direction trains along the segment; the root stores the observing train's own speed |
| `num_agents_ready_to_depart` | Number of trains ready to depart along the segment |

At the root, the main fields are the observing train's shortest target distance, malfunction counter, and speed. Several other fields initialize to 0. Interpret branch nodes as information along their segments. For example, root `num_agents_malfunctioning=8` means eight malfunction timing units remain for the observing train; the same field equal to 2 in a branch means two malfunctioning trains were recorded there.

#### Reading Child Branches

`childs` is a dictionary using `L`, `F`, `R`, and `B` for Left, Forward, Right, and Back. With a single exit, the tree orientation adjusts to that exit, so interpret labels together with track structure.

```python
from flatland.envs.observations import Node

if root is not None:
    forward_branch = root.childs.get("F")
    if isinstance(forward_branch, Node):
        print("Same-direction train count in the forward branch:",
              forward_branch.num_agents_same_direction)
```

`.get("F")` safely retrieves the forward branch and returns `None` if the key is absent. The environment also represents missing branches with negative infinity, usually `-np.inf`, where `np` is the common NumPy alias and `inf` means infinity. `isinstance(value, Node)` checks whether a value is an actual node. Positive infinity inside nodes may indicate that a target or event was not found within the explored range. Use the official normalized flattening component in Section 3.4 to process these values for neural networks.

In 4.3.0, `Node` has 12 numeric fields while the class's `observation_dim` property still says 11. Follow actual node fields when reading data. Obtain input length from the official flattening component's `get_len_flattened()`; depth 2 gives 252 values.

#### Using Conflict Prediction

You can supply `ShortestPathPredictorForRailEnv` when creating tree observations. It assumes trains follow shortest paths and predicts locations where they may meet. Its `max_depth=20` looks ahead twenty prediction time steps. When using potential-conflict features, record the predictor and horizon in experiment settings and assess prediction quality against actual policy behavior.

```python
from flatland.envs.observations import TreeObsForRailEnv
from flatland.envs.predictions import ShortestPathPredictorForRailEnv

tree_builder = TreeObsForRailEnv(
    max_depth=2,
    predictor=ShortestPathPredictorForRailEnv(max_depth=20),
)
```

### 3.3 Global Observations: Three Arrays for the Entire Map

Global observations return three NumPy arrays per train, ordered by map row, map column, and information channel. Channels are separate data layers over the same map, such as direction or malfunction information. These examples use a map with 30 rows and 30 columns.

```python
# observations comes from an environment using GlobalObsForRailEnv.
rail_map, train_map, target_map = observations[0]

print(rail_map.shape)    # (30, 30, 16)
print(train_map.shape)   # (30, 30, 5)
print(target_map.shape)  # (30, 30, 2)
```

`.shape` gives the length of each dimension. `(30, 30, 5)` means 30 rows, 30 columns, and five values per cell. The first two dimensions change with map size; channel counts stay fixed. Arrays currently use `float64`, or 64-bit floating point. Convert to `float32`, or 32-bit floating point, before training when needed.

#### Track Array rail_map

Each cell contains 16 connection flags describing possible exits for different incoming orientations. Four incoming orientations and four outgoing directions give sixteen combinations, derived from the environment's encoded transitions. Use the tutorial's `get_transitions()` query to read allowed exits for a train's current configuration directly.

#### Train Array train_map

| Channel | Content |
|---|---|
| 0 | Observing train's reference position and direction |
| 1 | Positions and directions of other unfinished on-map trains |
| 2 | Remaining malfunction counters for on-map trains |
| 3 | Speeds of on-map trains |
| 4 | Number of currently off-map trains whose origins are this cell |

Channel 0 may use the origin while waiting to depart and the target after completion. In channels 0 and 1, values 0, 1, 2, and 3 mean north, east, south, and west. Unfilled cells generally use -1. Malfunction and speed channels also generally use -1 for unfilled cells; the off-map train-count channel starts at 0. `train_map[3, 7, 2]` reads the malfunction value at row index 3 and column index 7. Python indices start at 0, so row index 3 is the fourth map row.

#### Target Array target_map

Channel 0 marks the observing train's destination, and channel 1 marks destinations of unfinished trains. Target cells contain 1; other cells contain 0. In 4.3.0, channel 1 also iterates over the observing train and can include its target. When multiple destination positions are allowed, the current global observation selects one configuration from `targets` to mark. Read the train object's `targets` for all alternatives.

Each train's global observation uses its own perspective, so channel 0 differs between trains 0 and 1. Read more complete task information, including timetables and intermediate stations, from train objects as explained in Section 4.3.

### 3.4 Official Flattened Tree Observations: Numeric Vectors Directly

These official components depend on Ray RLlib. Ray supports parallel computation, and RLlib is its reinforcement learning module. The project's `environment.yml` includes Ray 2.58.0 and RLlib dependencies. To synchronize an existing environment, run this command from the repository root.

```bash
conda env update -n cs5446-project -f environment.yml
```

`FlattenedTreeObsForRailEnv` returns fixed-length one-dimensional arrays directly. `FlattenedNormalizedTreeObsForRailEnv` additionally applies official scaling and clipping. Flattening arranges tree features into one array; normalization scales values into suitable ranges. The project selects these existing components directly.

```python
from flatland.ml.observations.flatten_tree_observation_for_rail_env import (
    FlattenedNormalizedTreeObsForRailEnv,
)

observation_builder = FlattenedNormalizedTreeObsForRailEnv(
    max_depth=2,
    observation_radius=2,
)
# Pass this object as obs_builder_object when creating the environment in Section 7.
```

With `max_depth=2`, each observation has shape `(252,)`: a one-dimensional array of 252 values from 21 nodes and 12 features per node. `observation_radius=2` scales distance features; `max_depth` still controls the explored branch levels. Arrays use 64-bit floating point by default and can be converted to 32-bit floating point for policy networks.

Official flattening orders features in three groups: six distances along segments, shortest target distances, and five train-information features. At depth 2, these groups contain 126, 21, and 105 values respectively. The normalized version scales and clips features by official rules. Read raw malfunction counters through `info["malfunction"][train_id]`. Keep the official feature order when converting observations to tensors.

## 4. Auxiliary info: Running Information for All Trains

### 4.1 Read by Category, Then Train ID

`info` contains four auxiliary categories for all trains. Access the category first and then the train ID. For example, `info["malfunction"][1]` reads train 1's remaining malfunction counter. This complete example illustrates the format and access methods.

```python
from fractions import Fraction
from flatland.envs.step_utils.states import TrainState

info_example = {
    "action_required": {0: True, 1: False},
    "malfunction": {0: 0, 1: 8},
    "speed": {0: Fraction(1, 1), 1: Fraction(1, 2)},
    "state": {0: TrainState.MOVING, 1: TrainState.MALFUNCTION},
}

print(info_example["malfunction"][1])   # 8
print(float(info_example["speed"][1]))  # 0.5
```

`Fraction(1, 2)` represents one-half in Python; `float()` converts it to 0.5. A speed counter may retain its previous value during a malfunction, so examine running state and position changes as well when assessing the situation.

| Category | Meaning | Recommended access |
|---|---|---|
| `action_required` | Whether the environment marks the train as needing an action | Read True/False per train |
| `malfunction` | Remaining malfunction counter | A positive value means malfunction timing remains |
| `speed` | Current speed-counter value | Convert to float for display or tensor processing |
| `state` | Train running state | Compare with the `TrainState` names below |

### 4.2 Interpreting Running States

| ID | Name | Meaning |
|---|---|---|
| 0 | `WAITING` | Waiting for departure timing conditions |
| 1 | `READY_TO_DEPART` | Ready to depart |
| 2 | `MALFUNCTION_OFF_MAP` | Malfunction before entering the map |
| 3 | `MOVING` | Moving |
| 4 | `STOPPED` | On the map and stopped |
| 5 | `MALFUNCTION` | Malfunction on the map |
| 6 | `DONE` | Destination task completed |

Compare names directly in code for clarity. For example, `info["state"][0] == TrainState.DONE` checks whether train 0 actually finished. Malfunction counters decrease during environment updates, while the state machine has its own update timing. At a boundary step, the counter may be 0 while the state remains a malfunction state. Interpret these situations primarily through the running state.

### 4.3 Reading Maps, Tasks, and Timetables

Default `info` contains the four fields above. Read the environment and train objects for more complete global information. Here, `agent` is train 0's object, which stores its task and current running data.

```python
agent = env.agents[0]
print("Origin:", agent.initial_configuration)
print("Current position:", agent.current_configuration)
print("Allowed destinations:", agent.targets)
print("Earliest departure:", agent.earliest_departure)
print("Latest arrival:", agent.latest_arrival)
```

Position and direction use `((row, column), direction)`, where row and column are zero-based indices and direction is a direction ID. `((3, 7), 1)` means fourth row, eighth column, facing east. `current_configuration` can be `None` before entering the map or after removal at arrival. Check before extracting positions.

| Information | Access path |
|---|---|
| Initial position and orientation | `agent.initial_configuration` |
| Current position and orientation | `agent.current_configuration` |
| All allowed destination configurations | `agent.targets`, a set of configurations |
| Destination configuration actually reached | `agent.target_configuration` |
| Earliest departure time | `agent.earliest_departure` |
| Latest arrival time | `agent.latest_arrival` |
| Actual arrival time | `agent.arrival_time`, None before arrival |
| Intermediate stations and timing requirements | `agent.waypoints`, `waypoints_earliest_departure`, `waypoints_latest_arrival` |
| Track map | `env.rail.grid` |
| Shortest distances from positions to targets | `env.distance_map.get()` |
| Elapsed time steps | `env._elapsed_steps` |
| Episode step limit | `env._max_episode_steps` |

The final two names begin with `_`, marking internal library fields. The project may later centralize time access in environment adaptation code so other modules retrieve time through project interfaces. The project separately defines and computes deadlock and conflict statistics, such as consecutive waiting times, mutually blocked train relationships, or movements prevented by the environment.

## 5. Reading Rewards and End Flags

`rewards[train_id]` stores the reward generated by this environment update. Default rewards are usually 0 at ordinary steps and negative for delays, unfinished tasks, and related penalties. Maintain a total per train and add step rewards after each step to obtain episode returns.

`dones[train_id]` checks one train's end flag, and `dones["__all__"]` checks the episode. Other trains can continue after one arrives early. Exit the loop when the episode ends and call reset to begin another.

```python
if dones["__all__"]:
    print("The episode has ended")
```

At the time limit, the environment marks all trains as done. For completion rate, count trains whose running state is `TrainState.DONE` and divide by total train count. With two trains and one arrival, the rate is 0.5. During training, separately record whether all trains arrived or the time limit was reached for subsequent value-target computation.

## 6. What to Save for One Training Transition

At minimum, save observations before the action, the action mask, action, action log probability, reward, observations after the action, and end flags. Save auxiliary information before and after actions too, so that decision requirements, malfunctions, and arrivals can be traced. Use a separate decision flag for steps without policy decisions and filter policy-update samples by that flag. Record the action requirement from the info used to select the current action.

Later updates may affect environment dictionaries and tree objects. Copy needed data when saving history or immediately convert it into independent arrays or tensors. Neural network inputs follow the selected official observation shape, and the sampler saves them in a consistent train order.

## 7. Complete Example: Print One Interaction

Activate `cs5446-project` and run the following code. It creates two trains, prints initial information, submits forward actions, and prints results. This example checks official data formats. First-version PPO action selection adds masks as described in Section 2.4. To inspect global observations, set `observation_builder` to `GlobalObsForRailEnv()`. To inspect official processed vector observations, use the normalized flattening component from Section 3.4.

```python
from flatland.envs.rail_env import RailEnv
from flatland.envs.rail_env_action import RailEnvActions
from flatland.envs.rail_generators import sparse_rail_generator
from flatland.envs.line_generators import sparse_line_generator
from flatland.envs.observations import (
    TreeObsForRailEnv, GlobalObsForRailEnv, Node,
)

observation_builder = TreeObsForRailEnv(max_depth=2)
env = RailEnv(
    width=30,
    height=30,
    number_of_agents=2,
    rail_generator=sparse_rail_generator(max_num_cities=2, grid_mode=True),
    line_generator=sparse_line_generator(),
    obs_builder_object=observation_builder,
    random_seed=42,
)

observations, info = env.reset(random_seed=42)
print("Initial running information:", info)

actions = {}
for train_id in env.get_agent_handles():
    actions[train_id] = RailEnvActions.MOVE_FORWARD

next_observations, rewards, dones, next_info = env.step(actions)
print("Submitted actions:", actions)
print("Step rewards:", rewards)
print("End flags:", dones)
print("Updated running information:", next_info)

for train_id, observation in next_observations.items():
    if observation is None:
        print("Train", train_id, "currently has no observation")
    elif isinstance(observation, Node):
        print("Train", train_id, "tree node fields:", observation._fields)
        print("Available child branches:", list(observation.childs.keys()))
    elif isinstance(observation, tuple):
        rail_map, train_map, target_map = observation
        print("Train", train_id, "array shapes:",
              rail_map.shape, train_map.shape, target_map.shape)
    else:
        print("Train", train_id, "vector shape:", observation.shape)
```
